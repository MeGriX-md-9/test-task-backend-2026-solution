# Ночная синхронизация CRM → PostgreSQL

Точка входа — `collect_leads_customers(is_full=True)` в `main.py`.

## Что было дорого

На каждую сущность выполнялись поиск по JSONB, запись и отдельный коммит. Поиск по логину мог читать несколько групп. После выгрузки сборщик повторно читал всю таблицу и коммитил очистку по частям.

## Что изменилось

- Сборщик один раз читает существующие группы через серверный курсор. По CRM ID и точному логину ищет в словарях, которые обновляются при изменении и слиянии. Совпадение по логину используется, только если оно указывает на одну группу.
- Покупатели без логина пропускаются. Сделка без совпадения создаёт новую группу. При слиянии сохраняется группа, найденная по ID сделки, и в неё записывается актуальная сделка. Контакты и компании объединяются по ID.
- После чтения обеих выгрузок полная синхронизация удаляет неприсланные сущности и сущности с «удалить» в имени без учёта регистра. Группы без покупателей и сделок удаляются. Частичная синхронизация сохраняет прежние фильтры статусов и пропускает очистку по выгрузке.
- Изменённые группы записываются пакетами по 500 через многострочный `INSERT`, `UPDATE … FROM (VALUES …)` и `DELETE … WHERE id IN (…)`. Один коммит на прогон. Ошибка CRM или записи откатывает всю операцию. Транзакционная блокировка PostgreSQL сериализует вызовы сборщика.

## Что сохранено

Формат JSONB с `general` и `api_value`, ID существующей группы и связь покупателя со сделкой через эту группу. Это позволяет внедрить изменение без переноса данных. GIN-индексы поддерживают поиск точных логинов и названий через `@>`, например `amo_leads @> '[{"general":{"name":"Название"}}]'`. Для существующей таблицы индексы добавляются скриптом [add_lookup_indexes.sql](add_lookup_indexes.sql), который нужно запускать через `psql` без общей транзакции.

## Оценка для 20 тыс. покупателей и 50 тыс. сделок

- **Запросы.** Два `SELECT` на уровне приложения, один коммит и по одному DML-запросу на каждые 500 вставляемых, изменяемых или удаляемых групп. При обновлении 70 тыс. групп это 140 DML-запросов. Серверный курсор дополнительно читает снимок примерно за 140 выборок по 500 строк. При полной замене 70 тыс. групп нужно около 280 DML-запросов. На 7 тыс. групп проверены 14 пакетных обновлений и 0 DML при повторе неизменной выгрузки.
- **Память.** На PostgreSQL 17 с 7 тыс. синтетических групп, одним контактом и описанием 2 КиБ на группу пиковый рабочий набор Python-процесса составил 134 МиБ при обновлении и 183 МиБ при полной замене. До прогона процесс занимал 60 МиБ. Линейная оценка на 70 тыс. групп с похожим JSON — около 0,8 ГиБ при обновлении и 1,3 ГиБ при замене. Пик зависит от объёма уже сохранённых данных и размера JSON.

## Запуск и проверки

Нужны Python 3.9+ и PostgreSQL. После активации виртуального окружения установите зависимости и запустите проверки, указав адрес тестовой БД.

```bash
python -m pip install -r requirements.txt
export TEST_DATABASE_URL='postgresql+psycopg://user:password@localhost/testdb'
python -m unittest discover -s tests -v
```

В PowerShell переменная задаётся через `$env:TEST_DATABASE_URL = '…'`. Тесты создают отдельную временную схему. Для вызова из приложения передайте `fetch=crm_fetch` в активном контексте Flask. Адаптер должен отдавать итераторы `Customer` и `Lead` и выбрасывать исключение при ошибке получения страницы. Боевой клиент CRM в задание не входил.
